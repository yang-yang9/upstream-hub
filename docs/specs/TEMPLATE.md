# Spec 模板

> 复制本文件到 `docs/specs/<feature>.md`，删除不适用的章节。**实现开始前** spec 必须先评审通过；实现过程中发现规格与事实不符时，先改 spec 再改代码。

---

## 背景

为什么需要这个能力：要解决的问题、涉及的用户场景、现状的不足。两三段以内。

## 行为规格

编号的验收标准，每条使用 Given-When-Then 结构。实现完成的定义 = 全部条目有对应测试且通过。

### AC-1: <一句话概括>

- **Given** <前置状态 / 输入>
- **When** <动作 / 触发>
- **Then** <可观察的期望结果>

### AC-2: …

## 边界用例

规格里容易踩坑的边界：空输入、零值、并发、时区、首次出现（无历史可对比）等。每条注明期望行为，同样要有测试。

## 非目标

明确不做什么，防止范围蔓延。这里列出的内容不实现、不测试，将来要做就新开 spec。

## 关联代码

规格对应的实现与测试位置（实现后回填）：

- 实现：`backend/internal/xxx/yyy.go` — 函数名
- 单元测试：`backend/internal/xxx/yyy_test.go` — 测试函数名
- 集成测试（如涉及持久化）：同上，标注 env 门控
